Chapter 1: The Failure of Discretionary Control (DAC)

The "Why": The Confused Deputy Problem

In standard Linux security, we use Discretionary Access Control (DAC). This is the user:group:permissions (rwx) model. It is "discretionary" because the owner of a resource has the discretion to grant access to others.

The fundamental flaw of DAC is that access is tied to Identity (Who you are) rather than Integrity (What you are doing).

This leads to the Confused Deputy Problem:
Imagine a web server process running as the user www-data. The www-data user has permission to read /var/www/html/index.html and write to /var/log/apache2/access.log. If an attacker exploits a buffer overflow in the web server, they "become" the www-data user. Because the system only checks who the user is, the attacker can now read any file owned by www-data or write to any log file. The "Deputy" (the web server) has been "Confused" into using its legitimate permissions to perform an illegitimate action.

Mandatory Access Control (MAC), implemented via SELinux, solves this. In MAC, the system (the Kernel) enforces a central policy that even the owner of a file cannot override. Even if you are root, if the SELinux policy says the httpd_t domain cannot read /etc/shadow, the kernel will block the request.

Core Concept: Subject vs. Object

To understand SELinux, you must stop thinking about "users" and start thinking about the relationship between Subjects and Objects.

1. The Subject (The Actor)

A Subject is an active entity in the system. In 99% of cases, a subject is a Process.

  • A subject is the entity that requests access to a resource.
  • A subject has a "security context" (a label) attached to it by the kernel.
  • Examples: A running Python script, a systemd daemon, a Podman container process, or a KVM hypervisor process.

2. The Object (The Target)

An Object is a passive entity. It is the resource being acted upon.

  • An object is the entity that receives the access request.
  • An object also has a security context attached to it.
  • Examples: A text file, a network port, a Unix socket, a block device, or a segment of system memory.

The SELinux Logic:
Access is granted IF (Subject_Label) is permitted to perform (Action) on (Object_Label).

Multi-Lens Analysis

The Architect's Perspective

The Architect does not design for users; they design for Isolation Boundaries.
When designing a system, the Architect defines the "Least Privilege" boundaries for every component. They decide which processes (Subjects) should be able to talk to which network ports (Objects) or which files (Objects). The goal is to ensure that if one layer (e.g., a Pod) is breached, the blast radius is mathematically limited by the policy.

The Blue Teamer's Perspective

The Blue Teamer uses SELinux as a Detection and Hardening tool.
Hardening involves moving the system from "Permissive" to "Enforcing" and tuning the policy so that no "Confused Deputy" attacks can succeed. Detection involves monitoring the auditd logs for AVC (Access Vector Cache) denials. A sudden spike in AVC denials for a specific process is a high-fidelity indicator of an attempted exploit or a misconfiguration.

The Red Teamer's Perspective

The Red Teamer views SELinux as a Barrier to Lateral Movement.
A successful Red Team operation involves:

  1. Enumeration: Identifying the SELinux context of the current process (ps -Z).
  2. Escalation: Attempting to find a "Domain Transition" vulnerability (moving from a restricted domain to a more privileged one).
  3. Evasion: Finding "Allowed" paths. If a policy allows httpd_t to write to a specific directory, the Red Teamer will attempt to use that "legitimate" path to plant a payload, rather than trying to access forbidden files directly.

The Integrated Example: The Lifecycle of a Request

To visualize the Subject/Object relationship across the stack, consider a single request:

  1. The Process (Subject): A web server process (httpd_t) starts.
  2. The Network Socket (Object): The process attempts to bind to TCP Port 80 (http_port_t). The kernel checks if the subject httpd_t has permission to bind to object http_port_t.
  3. The Unix Socket (Object): The process needs to communicate with a local database via a Unix Socket (httpd_sys_rw_content_t). The kernel checks if httpd_t can write to that socket.
  4. The Pod (Subject/Wrapper): In a containerized environment, the process is wrapped in a Pod. The Pod itself acts as a subject with a specific MCS Category (e.g., s0:c1,c2) to ensure it cannot touch other Pods.
  5. The VM (Subject/Wrapper): If the service is running inside a KVM Virtual Machine, the entire VM is treated as a single Subject (the virt_t domain) by the host kernel. The VM's virtual hard drive is the Object.

The fundamental flaw of DAC is that it cannot distinguish between a legitimate action and an exploited action performed by the same user. This is the Confused Deputy Problem: a high-privilege process (the Deputy) is tricked by an attacker into using its own permissions to perform an unauthorized task (e.g., a web server being used to overwrite /etc/shadow).

Mandatory Access Control (MAC), specifically via SELinux, shifts the logic from Identity to Policy. In MAC, even if you are root, the kernel checks a central, immutable policy to see if your Security Context is allowed to perform a specific action on a specific Object.

The Core Model: Subject vs. Object

To master SELinux, you must view the operating system as a collection of interacting entities. Every interaction is a relationship between a Subject and an Object.

1. The Subject (The Actor)

A Subject is an active entity that initiates an action.

  • Primary Form: A Process (and its associated threads).
  • Characteristics: A subject possesses a "Security Context" (a label) that defines its capabilities.
  • Lifecycle: Subjects are created by the kernel (via fork/exec) and inherit or transition into new contexts based on the policy.

2. The Object (The Target)

An Object is a passive entity that receives an action.

  • Forms: Files, Directories, Network Sockets, Unix Sockets, Network Ports, IPC (Inter-Process Communication) mechanisms, and Hardware devices.
  • Characteristics: An object possesses a "Security Context" that defines what kind of access is permitted to it.

The SELinux Decision Matrix:
When a Subject attempts to perform an Action (read, write, execute, bind, connect) on an Object, the kernel performs a lookup:
Can [Subject_Context] perform [Action] on [Object_Context]?
If the policy does not explicitly allow this, the kernel denies the request and generates an audit log.

Multi-Lens Analysis

The Architect's Perspective: Defining the Boundary

The Architect’s goal is to define the Isolation Boundary. They don't care about users; they care about the Minimum Viable Permission required for a service to function. When designing a system, the Architect maps out which Subjects (e.g., a Pod) must be isolated from which Objects (e.g., the Host's /etc directory or other Pods' memory).

The Blue Teamer's Perspective: Hardening and Detection

The Blue Teamer treats SELinux as the Last Line of Defense. If a service is compromised, the Blue Teamer relies on the fact that the Subject's context is restricted. They monitor for AVC (Access Vector Cache) Denials. A denial is a signal that either:

  1. An attacker is attempting to move laterally (Exploitation).
  2. The system configuration has drifted from the policy (Misconfiguration).

The Red Teamer's Perspective: Evasion and Transition

The Red Teamer views SELinux as a Logic Puzzle. Their objective is to find "holes" in the policy:

  1. Policy Over-privilege: Finding an object that is labeled too broadly (e.g., a file labeled system_u:object_r:public_content_t that actually contains sensitive data).
  2. Domain Transitions: Finding a way to trigger a process to move from a low-privilege domain to a high-privilege domain.
  3. Object Confusion: Attempting to use an allowed "Subject" to interact with an "Object" in a way the policy-writer didn't anticipate (e.g., using a permitted Unix Socket to manipulate a different service).

Chapter 2: The Identity Layer (SELinux Users and Roles)

In Chapter 1, we established that every interaction is a relationship between a Subject and an Object. To determine if that relationship is allowed, SELinux looks at the Security Context. The first two components of that context are the SELinux User and the Role.

It is critical to distinguish between a Linux User (UID) and an SELinux User.

  • Linux User (DAC): A UID (e.g., 0 for root, 1000 for bob) used to manage file ownership and permissions.
  • SELinux User (MAC): A label (e.g., system_u, user_u) used to define the security identity of a process.

1. The SELinux User: Beyond the Human

In SELinux, a "User" is simply an identity label. While humans are the most obvious users, they are only one type of identity in the system.

The Identity Spectrum

  1. Human Users: When a person logs in (via SSH, console, etc.), they are mapped to an SELinux user. Even if they are root in the DAC world (UID 0), they may be mapped to a restricted SELinux user like user_u.
  2. Service/System Users: These are non-human identities. Processes that start at boot (via systemd) or are spawned by the kernel are assigned SELinux users like system_u.
  3. Virtual/Isolated Users:
    • Pods/Containers: A process inside a Pod (managed by CRI-O or Podman) is often assigned a specialized SELinux user (e.g., container_u) to ensure that even if the process breaks out of the container namespace, it is still trapped by its identity.
    • VMs (KVM): The hypervisor process (the subject) managing a VM is typically system_u, but the identity context can be manipulated to ensure the VM's processes are isolated from the host's service identities.

The key takeaway: The SELinux User defines the "class" of identity. It is the foundation upon which Roles are built.

2. Roles and the Mechanism of Transition (sudo/su)

If the User is the identity, the Role is the set of permissions that identity is allowed to exercise. This is where the concept of Role-Based Access Control (RBAC) enters.

In SELinux, a User is mapped to one or more Roles. A Role, in turn, dictates which Types (Domains) a process can enter.

How sudo and su work in this context

In a standard Linux system, sudo or su are used to change your DAC identity (from bob to root). However, in an SELinux-enforced system, changing your UID is not enough to gain power. You must also perform a Role Transition.

  1. The Human State: You log in as bob. Your SELinux User is user_u and your Role is user_r. In this role, you can only enter the user_t domain (limited to personal files).
  2. The sudo Command: You run sudo su -.
    • DAC level: Your UID changes from 1000 to 0. You are now "root."
    • SELinux level: The kernel checks the policy. Does the user_r role have permission to transition to the sysadm_r (System Administrator) role?
    • The Transition: If permitted, your SELinux Role changes to sysadm_r. Now, you can transition into the sysadm_t domain, which allows you to manage system services, restart systemd units, and modify network configurations.

If the policy does not allow the role transition, you will be "Root in name only." You will have UID 0, but SELinux will still treat you as a user_r with no administrative privileges.

Chapter 3: The Policy Engine (Type Enforcement & the Anatomy of a Denial)

In the previous chapters, we defined the Subject (the Actor) and the Object (the Target). In this chapter, we look at the "Brain" that decides whether their interaction is permitted: Type Enforcement (TE) and the mechanism that records a failure: the AVC (Access Vector Cache) Denial.

1. Type Enforcement (TE): The Decision Logic

Type Enforcement is the primary mechanism of SELinux. Instead of granting permissions based on users, TE grants permissions based on the Type (the domain of the process and the type of the object).

The engine operates on a strict "Default Deny" principle. If a rule does not explicitly exist in the policy, the action is blocked.

The Core Logic: The Rule Structure

A Type Enforcement rule essentially looks like this in the policy source:
allow <subject_type> <object_type> : <class> <permission>;

Example:
allow httpd_t shadow_t : file read; — This rule would allow the web server to read the shadow file. If this rule is absent, the kernel blocks the attempt.

Booleans: The Policy Switches

Writing a new policy and recompiling it is a slow, heavy process. To manage this, SELinux uses Booleans.
Booleans are "on/off" switches within the compiled policy that allow administrators to change the behavior of the engine without reloading the entire policy.

Example: httpd_can_network_connect

  • If on: The policy allows httpd_t to create network sockets.
  • If off: The policy denies httpd_t from creating network sockets.

2. The Anatomy of a Denial (The AVC Message)

When the Policy Engine decides to block an action, it generates an AVC (Access Vector Cache) denial. This is the most critical piece of evidence for any security professional.

The Anatomy Breakdown

Consider this standard denial string:
avc: denied { read } for pid=1234 comm="httpd" name="secret.txt" dev="sda1" scontext=system_u:system_r:httpd_t:s0 tcontext=system_u:object_r:shadow_t:s0 tclass=file

To debug this, you must decompose it into its functional parts:

  1. denied { read }: The Action that was attempted.
  2. pid=1234 comm="httpd": The Subject identity (the specific process and its command name).
  3. name="secret.txt": The name of the Object being targeted.
  4. tclass=file: The Class of the Object (it is a file, not a socket or a directory).

The Critical Identities: scontext vs tcontext

This is where most engineers fail in their analysis. You must distinguish between the Source and the Target.

  • scontext (Source Context): This is the security context of the Subject (the process). It tells you who tried to do the action.

    • In our example: system_u:system_r:httpd_t:s0
    • Translation: A system user, in a system role, running in the httpd_t domain.

  • tcontext (Target Context): This is the security context of the Object (the resource). It tells you what they tried to touch.

    • In our example: system_u:object_r:shadow_t:s0
    • Translation: A system user, in an object role, labeled with the shadow_t type.

The Diagnostic Conclusion:
The httpd_t domain is attempting to read a file of type shadow_t. Since there is no allow httpd_t shadow_t : file read; rule in the policy, the kernel blocked it.

Multi-Lens Analysis

The Architect's Perspective: Policy Granularity

The Architect uses TE to ensure "Micro-Segmentation" at the process level. They don't just want to isolate a Pod from the host; they want to ensure that pod_process_a cannot even talk to pod_process_b via a Unix socket if they belong to different application tiers. They design the "Type" landscape so that the scontext and tcontext of different services have zero overlapping permissions.

The Blue Teamer's Perspective: Forensic Analysis

The Blue Teamer lives in the audit.log. When an alert triggers, their first step is to parse the scontext and tcontext.

  • If the scontext is a known service (like httpd_t), it’s likely a misconfiguration or a probe.
  • If the scontext is an unexpected process (like python_t trying to access shadow_t), it is a high-priority indicator of compromise.

The Red Teamer's Perspective: Finding the "Allow"

The Red Teamer's goal is to find an existing rule that they can exploit. They don't look for where the denied messages are; they look for where the allow rules are. They look for "Over-privileged Types." If they find a process where the scontext is something common like unconfined_t, they have essentially bypassed the entire TE engine.

Chapter 4: Hierarchical & Compartmentalized Security (MLS and MCS)

In previous chapters, we focused on Type Enforcement (TE), which is the heart of the "Targeted" policy. In a Targeted policy, security is based on the Type (e.g., httpd_t). However, TE alone does not account for sensitivity (how secret a file is) or multi-tenancy (how to keep two identical processes from touching each other's data).

To solve this, SELinux provides MLS and MCS.

1. The Crucial Distinction: Targeted vs. MLS/MCS

Before diving in, a vital technical distinction must be made: You cannot simply "turn on" MLS or MCS in a standard Targeted policy.

  • Targeted Policy (The Default): This is what 99% of Linux servers run. It uses TE to protect specific, high-risk services (like web servers or databases) but leaves most other processes in a relatively unconstrained domain. It does not use sensitivity levels or categories.
  • MLS/MCS Policies: These are specialized policy frameworks. To use MLS, you must load an MLS Policy, which is significantly more complex and restrictive than the Targeted policy.

Can you mix them?
You cannot run two different policy engines (Targeted and MLS) simultaneously. However, modern implementations use a "hybrid" logic: The Targeted policy can be extended to use MCS (Multi-Category Security) to facilitate container isolation. This is how we get the best of both worlds: Type Enforcement for system services and MCS for container multi-tenancy.

2. MLS: Multi-Level Security (The Hierarchy)

MLS is designed for high-security environments (government, military) where information is classified by Sensitivity Levels. It is based on the Bell-LaPadula Model, which focuses on confidentiality.

The Logic of Levels

MLS uses a hierarchical scale. For example:
Top Secret > Secret > Confidential > Unclassified

The Two Golden Rules of MLS:

  1. No Read Up: A subject at the Secret level cannot read an object at the Top Secret level.
  2. No Write Down: A subject at the Top Secret level cannot write information into an object at the Secret level (this prevents "leaking" secrets to lower levels).

In an MLS context, the security label looks like this:
user_u:role_r:type_t:s0:c0.c1
The s0 represents the Sensitivity Level.

3. MCS: Multi-Category Security (The Compartment)

While MLS is about Vertical Hierarchy (levels), MCS is about Horizontal Isolation (categories). MCS is the "operational" version of MLS used heavily in cloud-native environments like Podman, CRI-O, and Kubernetes.

The Logic of Categories

Instead of levels, MCS uses Categories (also called compartments). These are non-hierarchical. For example, a process might belong to Category A and Category B.

The "Container Isolation" Use Case

Imagine you are running two separate customer web applications in two different Pods on the same host. Both processes have the same Type (container_t).

  • If we only used TE, Container_A could potentially access the files of Container_B because they share the same Type.
  • With MCS: The runtime assigns a unique category to each container.
    • Pod A: container_t:s0:c1,c2
    • Pod B: container_t:s0:c3,c4

Even though both are container_t, the kernel sees that the Subject (c1,c2) does not have permission to access the Object (c3,c4). The containers are horizontally isolated.

Multi-Lens Analysis

The Architect's Perspective: Designing for Multi-Tenancy

The Architect uses MCS to build Multi-Tenant Infrastructures. They rely on the container runtime to automatically inject unique MCS categories into every Pod. This allows the Architect to host multiple customers on a single high-density host with the mathematical certainty that one customer's process cannot "reach sideways" into another's data, even if they are running the same software.

The Blue Teamer's Perspective: Detecting Cross-Tenant Probes

The Blue Teamer monitors for AVC denials where the scontext and tcontext have different Categories.

  • A denial like scontext=container_t:s0:c1 tcontext=container_t:s0:c2 is a massive red flag. It indicates that a process in one container is actively attempting to probe or access a resource belonging to another container.

The Red Teamer's Perspective: Category Exhaustion & Escapes

Chapter 5: The Execution & Integration Layer (Kernel, Systemd, and the Stack)

In the previous chapters, we dealt with the "Logic" of SELinux (Rules, Users, Roles, and Types). In this chapter, we bridge the gap between theory and reality. We will examine how a request moves from a user-space command, through the system management layer, and into the kernel to be adjudicated by the SELinux engine.

1. The Interceptor: The Kernel and the LSM

The SELinux engine does not live in your applications; it lives in the Linux Kernel.

The mechanism that allows this is the LSM (Linux Security Module) framework. The kernel contains "hooks" placed at critical points in the execution path—specifically during System Calls (syscalls).

The Workflow of a Syscall:

  1. The Request: A process (Subject) issues a syscall, such as open(), connect(), or write().
  2. The Hook: Before the kernel executes the requested action, it hits an LSM Hook.
  3. The Query: The kernel pauses the syscall and asks the SELinux engine: "Subject [Context A] wants to perform [Action] on Object [Context B]. Is this allowed?"
  4. The Decision:
    • Allowed: The kernel continues the syscall and completes the task.
    • Denied: The kernel aborts the syscall, returns an error (usually EACCES - Permission Denied) to the process, and triggers an AVC Denial in the audit logs.

2. The Birth of a Subject: Systemd

If the kernel is the judge, Systemd is the "Registrar." When you start a service via systemctl start nginx, Systemd is responsible for spawning that process. Crucially, Systemd defines the initial Security Context of that process.

The systemd Integration

Systemd unit files can explicitly define the SELinux context of a service using the SELinuxContext= directive.

More importantly, modern Systemd versions provide Sandboxing Directives that work in tandem with SELinux to reduce the attack surface. While SELinux manages the labels, Systemd can manage the visibility of the filesystem (e.g., ProtectSystem=strict, ProtectHome=true).

The Architect's View: A robust architecture uses Systemd to restrict the "view" of the process (Namespaces) and SELinux to restrict the "actions" of the process (MAC).

3. The Hierarchy of Abstraction: The Stack

In modern infrastructure, we rarely deal with raw processes. We deal with layers of abstraction. To master SELinux, you must understand how the Subject/Object model scales up the stack.

Layer 1: The Process (The Atomic Subject)

The most basic unit. A single execution flow with a single PID and a single SELinux context.

Layer 2: The Sockets (The Communication Objects)

When processes talk, they use Objects.

  • Unix Sockets: Used for Inter-Process Communication (IPC) on the same host. The socket itself is a file-like object with its own type (e.g., container_runtime_t).
  • Network Sockets: Used for network communication. The "Object" here is the Network Port (e.g., http_port_t). The kernel checks if the process's type has permission to bind to or connect to that port type.

Layer 3: The Pod (The Containerized Group)

A Pod (in Podman/CRI-O) is a logical grouping of processes.

  • The Subject: To the kernel, a Pod is not a single entity; it is a collection of processes. However, the Container Runtime ensures that all processes within that Pod share the same MCS Category (e.g., s0:c1,c2).
  • The Difference: Unlike a single process, a Pod's identity is tied to a shared namespace. The SELinux engine ensures that even if two processes have the same Type, they are isolated by their Category.

Layer 4: The VM (The Hypervisor Wrapper)

A Virtual Machine (KVM) is the highest level of abstraction.

  • The Subject: The entire VM is represented on the host by a single, massive process (usually qemu-kvm). This process is the Subject.
  • The Object: The VM's virtual disk (the .qcow2 file) is the Object.
  • sVirt (The Magic Link): This is a technology that uses SELinux to automatically assign a unique MCS category to every single VM process. This ensures that VM_A (the subject) cannot access the disk image of VM_B (the object), even though both are running under the same hypervisor process type.

Multi-Lens Analysis

The Architect's Perspective: Defense in Depth

The Architect designs "Nested Security."

  1. Systemd isolates the service's filesystem view.
  2. SELinux (TE) restricts the service's ability to use syscalls.
  3. SELinux (MCS) isolates the service from other tenants (Pods/VMs).
    This creates a layered defense where a failure in one layer (e.g., a container escape) is caught by the next (the host's SELinux policy).

The Blue Teamer's Perspective: Mapping the Stack

The Blue Teamer must be able to trace an error back through the layers. If a database cannot read a file, the Blue Teamer must determine:

  • Is it a Process error (the wrong type)?
  • Is it a Socket error (the port isn't labeled)?
  • Is it a Pod error (the MCS category is mismatched)?
  • Is it a VM error (the hypervisor process doesn't have access to the virtual disk)?

The Red Teamer's Perspective: Breaking the Wrapper

The Red Teamer looks for "Wrapper Escapes."

  1. Container Escape: Moving from a container_t (Subject) to a system_t (Host Subject) by exploiting a kernel vulnerability.
  2. VM Escape: Moving from the guest environment to the host by exploiting the qemu-kvm process (the Subject).
  3. Socket Hijacking: If a process is allowed to talk to a Unix Socket, the Red Teamer attempts to use that socket to send commands to a more privileged service.

Chapter 6: The Observability Loop (Modes and Auditing)

In the previous chapters, we covered the "How" (Mechanisms) and the "What" (Policies). In this final conceptual chapter, we cover the "State" of the engine. How do we know if the engine is active, how do we tell it to "just watch" for a moment, and how do we read the "black box" when something goes wrong?

1. Modes of Operation: The Engine's State

The SELinux engine can exist in three primary states. Understanding these is critical for both system stability and security forensics.

1. Enforcing Mode

This is the only mode used in a production-hardened environment. In this mode, the kernel actively blocks any action that violates the policy.

  • Behavior: Subject attempts action →\rightarrow→ Policy check fails →\rightarrow→ Kernel blocks action →\rightarrow→ AVC denial is logged.

2. Permissive Mode

In this mode, the engine "simulates" enforcement. It does not block any actions, but it logs every single violation that would have been blocked in Enforcing mode.

  • Behavior: Subject attempts action →\rightarrow→ Policy check fails →\rightarrow→ Kernel allows action →\rightarrow→ AVC denial is logged.
  • The Danger: Permissive mode is often used for "troubleshooting," but it is a False Sense of Security trap. If a system is left in Permissive mode, the security boundaries are effectively gone, and the system is running in a DAC-only environment, despite the logs suggesting SELinux is "active."

3. Disabled Mode

The SELinux engine is completely turned off. The kernel does not load the security modules, and no security contexts are applied to objects.

  • Behavior: The engine is non-existent. There is no MAC enforcement and no SELinux auditing.

2. The Observability Loop: The Audit Lifecycle

Observability is the ability to reconstruct the "why" of a system decision. This is achieved through the Audit Lifecycle.

The Lifecycle of a Denial:

  1. The Event: A Subject (e.g., a Pod process) attempts a forbidden action on an Object (e.g., a host file).
  2. The Interception: The Kernel LSM hook catches the syscall.
  3. The Decision: The SELinux engine determines the action is a violation.
  4. The AVC Generation: The kernel generates an Access Vector Cache (AVC) denial message.
  5. The Handoff: The kernel passes this message to the auditd (Audit Daemon) subsystem.
  6. The Persistence: auditd writes the message into the audit logs (typically /var/log/audit/audit.log).

The Importance of auditd

While SELinux generates the signal, auditd is the mechanism that captures and preserves it. Without a properly configured audit daemon, the "evidence" of a security breach or a misconfiguration may be lost in the kernel's volatile memory.

Multi-Lens Analysis

The Architect's Perspective: Designing for Observability

The Architect ensures that the system is "Auditable by Design." This means:

  1. Ensuring auditd is configured with sufficient disk space and rotation policies to prevent log loss.
  2. Integrating SELinux audit logs into a centralized SIEM (Security Information and Event Management) system.
  3. Designing systems so that "Permissive" mode is a temporary, strictly controlled state used only in staging, never in production.

The Blue Teamer's Perspective: Real-time Response

The Blue Teamer uses the observability loop for Active Defense. They set up real-time alerts based on AVC denial patterns.

  • A single denial might be a developer error.
  • A burst of denials from a single scontext (Subject) targeting multiple tcontexts (Objects) is a high-fidelity alert for an active exploitation attempt.

The Red Teamer's Perspective: Policy Mapping

The Red Teamer loves Permissive Mode. If they can convince a sysadmin to put a system into Permissive mode "just to see if it works," the Red Teamer can perform all their reconnaissance, scanning, and exploit attempts without being blocked. They use this time to map the exact boundaries of the policy, effectively creating a "blueprint" of the security architecture so they can plan a silent, non-denial-triggering attack once the system returns to Enforcing mode.

Final Summary: The SELinux Mental Model

When you face a security problem in Linux, do not ask "Who is the user?" Instead, run this mental algorithm:

  1. Identify the Subject: What is the PID? What is its scontext (User:Role:Type:Level)?
  2. Identify the Object: What is the file/socket/port? What is its tcontext?
  3. Identify the Action: Is it a read, write, execute, bind, or connect?
  4. Analyze the Failure:
    • If the Types don't match →\rightarrow→ Type Enforcement (TE) issue.
    • If the Categories (e.g., c1,c2) don't match →\rightarrow→ MCS issue (Multi-tenancy/Container isolation).
    • If the Levels (e.g., s0 vs s1) don't match →\rightarrow→ MLS issue (Sensitivity/Classification).
  5. Determine the Fix:
    • Misconfiguration? →\rightarrow→ Use restorecon or semanage fcontext.
    • Legitimate Need? →\rightarrow→ Use semanage port or write a custom .te policy.
    • Policy Switch? →\rightarrow→ Use setsebool.

Rapid-Fire Glossary

The Core Architecture

  • MAC (Mandatory Access Control): System-enforced security that overrides user discretion.
  • DAC (Discretionary Access Control): Standard Linux rwx permissions based on UID/GID.
  • LSM (Linux Security Module): The kernel framework that provides the "hooks" for SELinux to intercept syscalls.
  • AVC (Access Vector Cache): The kernel's high-speed cache for access decisions; when a decision is denied, an AVC Denial is generated.

The Identity Components (The Context String)

  • User (u): The SELinux identity (e.g., system_u, user_u).
  • Role (r): The set of permissions assigned to a user (e.g., sysadm_r, user_r).
  • Type (t): The primary label for both processes (Domains) and objects (Types).
  • Level/Category (s0:c1,c2): The hierarchical (MLS) or compartmentalized (MCS) identifier.

The Isolation Models

  • Type Enforcement (TE): The "Vertical" security model (Process Type →\rightarrow→ Object Type).
  • MCS (Multi-Category Security): The "Horizontal" security model (Isolation between identical types using categories).
  • MLS (Multi-Level Security): The "Hierarchical" security model (Information sensitivity levels).
  • sVirt: The integration of SELinux and KVM that uses MCS to isolate VM processes from each other and the host.

The Debugging Toolkit

  • scontext: The security context of the Source (the Subject/Process).
  • tcontext: The security context of the Target (the Object/Resource).
  • tclass: The classification of the object (e.g., file, socket, dir, tcp_socket).
  • sealert: The primary tool for human-readable, actionable SELinux error analysis.
